# ADR-0001 Контракты API, карточки методов и модели данных хранятся в git

## Контекст

- Описания методов и модели данных сейчас ведутся в Confluence (Data Center). Схемы копируются в несколько страниц и расходятся с реальной реализацией через 1–2 релиза.
- История изменений страниц Confluence не показывает понятный diff по полям контракта. Нет механизма «согласовано именно это содержимое».
- Статус согласования в Confluence без плагинов ведётся вручную (метки, макрос Status) и не защищён от изменения.
- Разработка уже работает в корпоративном git, контракты (Swagger) и ERD (dbdiagram) частично лежат там же.

## Рассмотренные варианты

| Критерий | A. Всё в Confluence | B. Гибрид: контракты и модели в git, ТЗ в Confluence | C. Всё в git, включая ТЗ |
|---|---|---|---|
| Актуальность контрактов | Низкая: ручное копирование | Высокая: один источник | Высокая |
| История и diff | Слабые | Полные для технических артефактов | Полные |
| Фиксация согласования | Вручную, не защищена | PR approvals для технических артефактов; ТЗ — по текущему процессу | PR approvals для всего |
| Удобство для бизнеса | Высокое | Высокое: бизнес работает в Confluence как раньше | Низкое: нужен PDF или чтение PR |
| Порог входа для аналитиков | Нет | Средний: git, PR (1–2 часа обучения) | Выше: ТЗ тоже в Markdown |
| Автоматические проверки | Нет | Да: линтеры API и ERD, связность | Да |
| Плагины / права администратора | Для статусов — нужны | Не нужны | Не нужны |

## Решение

Выбираем **вариант B (гибрид)**.

- В git: OpenAPI-контракты, карточки методов, ERD (DBML), sequence-диаграммы, интеграционные паспорта, ADR.
- В Confluence: BRD, ТЗ на флоу, описание экранных форм, обзорные страницы систем со ссылками на git.
- ТЗ ссылается на артефакты git по тегу или коммиту.
- Согласование технических артефактов — через Pull Request с обязательными одобрениями.

Процесс описан в `PROCESS.md`.

## Последствия

- **Положительные:**
  - один источник истины для контрактов;
  - неизменяемая история согласований;
  - автоматические проверки в CI;
  - процесс не зависит от плагинов Confluence.
- **Отрицательные / что принимаем:**
  - аналитикам нужно базовое владение git;
  - для внешних потребителей документацию собираем отдельно (HTML/PDF из CI);
  - на переходный период часть старых методов остаётся в Confluence с баннером-ссылкой.
- **Что нужно сделать:**
  1. Создать репозиторий; защитить `main`; настроить правила одобрений и CI.
  2. Пилот на одной системе: 3–5 методов.
  3. Обучить аналитиков.
  4. Добавить баннер на старые страницы методов в Confluence.
